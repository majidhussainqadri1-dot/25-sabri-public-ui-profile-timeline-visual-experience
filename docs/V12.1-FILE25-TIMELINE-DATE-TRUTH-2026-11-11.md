# File 25 — V12.1 V12-026: Timeline publication/update date truth

**Date:** 11 November 2026. **Frozen source parent:** `0c4c55fff4115a37a69c47c692d5fd8113a4b531` (Draft PR #44, unmerged). This report is source-based; live deployed parity, installed File21 and database versions are unverified.

## Confirmed source root cause
`Future_Public_Experience::timeline_meta()` projected `updated_at` using `$item['updated_at'] ?? $item['published_at']`. Its JavaScript consumer then invariably rendered the value as **Updated**, even when the only owner-supplied date was the publication timestamp. This conflates two distinct source facts and violates the plan's V12-026 requirement for truthful freshness/source dates.

## Bounded correction
- Preserve separate `updated_at` and `published_at` values in File25's ephemeral public presentation metadata; do not edit native File21 content or invent a modification event.
- In the browser, use a credible explicitly supplied update date first, or show a credible publication timestamp labelled **Published**. Invalid/future dates do not appear as current information (allow five minutes of clock skew). Both labels are localizable.
- Expand `tests/future-public-experience.php` with actual private-method projection regression cases: publication-only, genuine update, malformed update with valid publication; plus JS source-contract assertions. Existing PHP8.0/8.3, JS syntax and deterministic package checks must be rerun at the exact new head.

## Remaining gates
Real owner-provider data, multi-locale date formatting, RTL/LTR, screen-reader announcement, actual browser DOM, File24 privacy assurance and Hostinger staging remain pending. The change is not a live-fix claim.
