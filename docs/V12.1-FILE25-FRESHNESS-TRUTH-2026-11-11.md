## One confirmed source root cause
`Future_Public_Experience::freshness()` previously accepted valid-looking ISO dates in the future as already completed updates. The Profile overview client code used `fresh.label || updated date`, permitting a source label to suppress the actual date from visible and spoken text; Timeline card updates also lacked a future timestamp check. These are three manifestations of one presentation problem: **owner-source timestamp is not reliably bound to the freshness label seen by users**.

## Bounded File25-only correction
1. Suppress future profile content-update timestamps beyond a five-minute server clock-skew allowance. Never fabricate or rewrite a File03/File21 record.
2. Make the owner-provided update date visible in a real `<time datetime>` element. Preserve any owner note as separate supplemental text rather than letting it replace the date.
3. Apply the same **server-authoritative** freshness guard to Timeline card metadata, without modifying canonical post published/updated facts. Avoid using the visitor's device clock as the authority, since a mis-set phone clock could suppress a valid timestamp.
4. Add an actual PHP regression around `Future_Public_Experience::freshness()` for previous day, future day, small clock skew, invalid calendar date and malformed payload, plus a static checked-in JS source assertion; add actual Timeline metadata fixtures for future and valid historical dates. Do not overstate the JS assertion as a browser test.

## Second adversarial review — device-clock skew
A first client-side guard compared parsed dates to `Date.now()`. On a visitor device whose clock lags, that would conceal legitimate owner updates. The correction instead computes the five-minute future guard **once on the server** in `safe_update_time()`, shared by profile freshness and Timeline metadata. JavaScript now only validates parseability and displays the server-vetted source date. No browser-local time is used to deny owner-provided timestamp presentation.

## Later owner-truth decision (PR46 source, 11 November 2026)
The earlier section correctly describes **date parsing and invalid/future time protections**, but a second independent source audit of PR #16 demonstrated a separate authorization gap: an ordinary UI filter could invent the entire Profile-wide last-updated claim in the first place. A syntactically correct recent timestamp is not native provenance. Until File03/21 publishes a versioned public-safe Profile freshness DTO, `Future_Public_Experience::freshness()` now returns `[]`, and hostile generic filter values are suppressed. `safe_update_time()` and valid native Timeline item dates continue to function; they are not disabled. The actual profile freshness feature remains **owner-blocked**, not finished.
